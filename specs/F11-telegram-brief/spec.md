## 1. Problem statement

Marco wants to read the site's AI news brief in a private Telegram conversation
each morning. Reuse the brief generated by the offline pipeline, with dates and
source links, and deliver it after the daily site update without another model
call or an always-running server.

User stories:
- As Marco, I want a concise morning message so I do not have to remember to
  open the website.
- As the maintainer, I want a local preview and clear delivery results so I can
  verify formatting and diagnose failures without exposing credentials.

## 2. Constraints

- Preserve the static GitHub Pages site and existing public news data contract.
- Use the existing Node/TypeScript ESM stack and GitHub Actions pipeline.
- Deliver to one configured private Telegram chat only, using the official Bot
  API; credentials live in ignored local `.env` and GitHub Actions secrets.
- Keep the current daily 06:00 UTC schedule, including weekends. Delivery follows
  successful ingestion and deployment; no exact-minute arrival guarantee.
- English, existing 3–5 brief bullets, existing source citations, and a site link.
- No additional LLM generation for delivery. F10 controls the underlying models.
- Setup and verification instructions must work in Windows cmd.
- No new Telegram SDK dependency is needed; native HTTP requests are sufficient.

## 3. Non-goals

- No conversational AI, incoming command loop, webhook server, or MCP integration.
- No public subscriptions, groups, multiple recipients, email, or WhatsApp.
- No new personal-ranking prompt or separate personal summary in the first version.
- No exact-once delivery guarantee across ambiguous network failures; prefer
  requiring manual resolution over blindly risking duplicate messages.
- No automatic account creation, credential purchase, or credentials in browser
  assets, tracked files, command-line arguments, or printed request URLs.

## 4. Interfaces & data shapes

Input is existing `public/news.json`, specifically its validated brief:

```json
{
  "generatedAt": "2026-09-06T06:05:00Z",
  "bullets": [
    {"text": "First development and its significance.", "refs": ["https://example.org/story-one"]},
    {"text": "Second development and its significance.", "refs": ["https://example.org/story-two"]},
    {"text": "Third development and its significance.", "refs": ["https://example.org/story-three"]}
  ]
}
```

The example is a brief object, not a replacement schema for the news archive.

Configuration:
- `TELEGRAM_BOT_TOKEN` — secret from BotFather.
- `TELEGRAM_CHAT_ID` — the owner's private chat ID, stored as a string.
- `TELEGRAM_ENABLED=true` — explicit scheduled-delivery opt-in; false/unset skips.

Proposed commands (available only after implementation):
- `npm run telegram:preview` — render the existing brief and eligibility reason;
  no API request, credential requirement, or delivery-state mutation.
- `npm run telegram:send` — validate freshness, recipient, and durable delivery
  state, then send only when eligible.
- `npm run telegram:setup` — after the owner sends `/start` to the new bot,
  obtain private-chat setup information without exposing the token or message
  contents. Never select a recipient silently if multiple private chats appear.

Output: one message headed `AI Morning Brief — YYYY-MM-DD`, bullets with numbered
source links, generation time displayed in Europe/London, and a link to the site.
Escape text safely for Telegram formatting, allow only HTTP(S) citations, and
keep the message within 4096 characters after entity parsing. Oversized briefs
become an explicitly shortened preview with the full-brief site link; never
silently split one delivery into several notifications.

Delivery results are concise, e.g. `Telegram: sent`, `Telegram: skipped (disabled)`,
`Telegram: skipped (stale brief)`, `Telegram: skipped (already sent)`, or
`Telegram: delivery uncertain; check your chat before retrying`.

Durable delivery state is separate from published news/site files. It records a
brief identity and pending/sent/uncertain outcome, without storing bot tokens,
chat IDs, or message bodies in tracked/public state. The implementation plan
must define persistence and concurrency before code is approved; an ephemeral
runner file or best-effort cache alone does not satisfy this requirement.

## 5. Edge cases

- No new brief, invalid timestamp, future timestamp, or brief from an earlier
  Europe/London calendar day: skip with an explicit reason. Validate
  `brief.generatedAt`, not only the archive timestamp. Carry-forward content
  must not be relabeled as today's brief.
- Missing/malformed archive or invalid brief: fail the delivery step safely;
  never modify the archive or fabricate a summary.
- Disabled delivery: skip. Enabled delivery with missing credentials: fail with
  a message naming the missing variable; keep the completed website deployment.
- Already-sent brief or another successful delivery on the same London date:
  skip. Serialize overlapping workflow attempts and read authoritative state.
- Telegram returns an explicit 429 rejection: honor a valid `retry_after` within
  a bounded retry/time budget; report failure if the budget is exceeded.
- Invalid token, inaccessible chat, or bot blocked: actionable error, no retry
  storm, and no credentials or raw request URLs in logs.
- Timeout, uncertain server response, or interruption after a request may have
  reached Telegram: preserve an uncertain/pending outcome and require explicit
  recovery. Do not automatically repeat the send on a rerun.
- Unable to persist/read delivery state: do not initiate a send. If recording a
  successful result fails, preserve the prior pending marker for recovery.
- Text contains markup, emoji, invalid URLs, or unusually long citations:
  escape/sanitize and shorten safely; keep the website link and disclosure.
- Telegram fails after deployment: the website stays published, but the
  workflow visibly reports delivery failure instead of claiming total success.

## 6. Acceptance criteria

1. WHEN a scheduled run produces and publishes an eligible brief THEN the sender
   SHALL deliver one dated message to the configured private chat with summary
   text, source links, and the website link, without another LLM call.
2. WHEN delivery is disabled, stale, or already completed THEN the sender SHALL
   make no send request and SHALL print the matching skip reason.
3. WHEN the same run is retried or overlaps another run THEN persistent state
   and serialization SHALL prevent automatically resending a completed or
   uncertain delivery; successful daily delivery SHALL be limited to one.
4. WHEN a Telegram API or state-storage failure occurs THEN the sender SHALL
   follow the recovery rules in section 5 and SHALL preserve the published site.
5. WHEN preview runs THEN it SHALL show the rendered content and eligibility
   without network requests, credentials, or state mutation.
6. WHEN automated checks run without secrets THEN they SHALL cover formatting,
   freshness around London date/DST boundaries, duplicate/uncertain outcomes,
   concurrency, and API failures with mocked transport and state storage.
7. WHEN setup documentation is followed THEN Marco SHALL be able to create the
   bot, start its private chat, store credentials locally/in Actions, preview,
   and perform one live delivery without copying secrets into source code.
8. WHEN content exceeds Telegram limits THEN the sender SHALL emit a valid
   single shortened message with disclosure and a link to the full brief.
